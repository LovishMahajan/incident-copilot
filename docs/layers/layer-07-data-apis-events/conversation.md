## Questions and answers

### Q7.1 An incident arrives without a globally unique reference. How should the platform identify it across requests, workflows and services?

**Frame.** What single identifier follows an incident everywhere?

**Knowns.** Artifact 4: intake returns an incident ID immediately; the workflow, timeline, traces and audit all carry it.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** The platform assigns every incident its own ID at intake. It doesn't rely on the monitoring system's reference.

- **`incident_id`****:** a UUIDv7, generated by the application. It is unique everywhere, and sorts by creation time, which keeps indexes efficient.
- **`display_ref`****:** a short, human reference, such as `INC-2026-000123`, for chat and conversation. It's never used as a key.
- **Everywhere the same ID:** the Temporal workflow ID is `incident-<incident_id>`, and every event, trace, log line and artifact carries `incident_id`.
- **Monitoring's own ID** is kept as `source_alert_id` on each alert, so the two can be matched.

### Q7.2 The platform supports hundreds of applications and multiple environments. How should each incident be associated with its corresponding service and environment?

**Frame.** How is each incident tied to exactly one service and environment?

**Knowns.**

- Artifact 2: one organisation and one environment now, but records are tagged with an organisation ID.
- Artifact 4: the service must match the catalogue.

**Unknowns.** How the service catalogue is kept in sync.

**Assumptions (provisional).**

- The service catalogue can be synchronised into the platform daily, and on change. *Owner: Platform owner. Validated when: a sync job runs against the catalogue.*

**Answer.**

- **`services`** **and** **`environments`** **tables**, each keyed by its own ID, and unique by `(org_id, slug)`.
- **Every incident has** **`service_id`** **and** **`environment_id`** as required foreign keys, so an incident can't exist without both.
- **Requests use slugs** (for example `checkout`, `production`). Intake resolves them to IDs, and rejects unknown values (FR-06).
- **Every action names its own target** service and environment, which is checked against the incident's.
- **`org_id`** is on every top-level record.

### Q7.3 An engineer collects a log, a metric and a distributed trace. How should each piece of collected information be represented as a reusable record?

**Frame.** How do different kinds of evidence share one record shape?

**Knowns.** Artifact 3 lists the kinds of evidence; Artifact 4 requires source, time and link on every item.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** **One** **`evidence`** **record type for every kind**, with:

- **common columns** for what every item has: kind, source, time window, collection time, link, summary and fingerprint
- **an** **`attributes`** **field** for what varies by kind:
    - **log:** level, logger, message template, count
    - **metric:** name, labels, aggregation, values
    - **trace:** trace ID, failing span, duration
- **a snapshot** of the raw data in the artifact store, referenced by `artifact_id`

Hypotheses, diagnoses and tests then refer to evidence by `evidence_id`, whatever its kind. A gap is also an evidence record (`kind = gap`), so missing sources are visible in the same list.

### Q7.4 Evidence records need to be independently verified and traced back to their origin. Which attributes should every evidence record contain?

**Frame.** What lets anyone check an evidence item, and find where it came from?

**Knowns.** Artifact 4 (FR-07) and Artifact 5: source, time, link; redaction; injection flag.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

| **Attribute** | **Purpose** |
| --- | --- |
| `evidence_id`, `incident_id` | Identity |
| `kind` | What type of evidence |
| `source_system` | Which tool it came from |
| `collected_by` | Which component or person collected it |
| `query` | The exact query used, so it can be rerun |
| `window_start`, `window_end` | The time the data refers to |
| `collected_at` | When it was collected |
| `source_link` | Link to the original in the source tool |
| `artifact_id` | Snapshot of the raw data, kept even if the source expires it |
| `content_sha256` | Fingerprint, proving the snapshot hasn't changed |
| `summary` | Short, redacted extract used in prompts |
| `is_partial` | The source was degraded |
| `flagged_injection` | The content looks like an instruction (Artifact 5) |

Evidence records are **append-only:** never edited or deleted (until retention ends).

### Q7.5 An investigation generates four competing explanations for the same failure. How should the platform represent and distinguish these hypotheses?

**Frame.** How do we store several explanations side by side?

**Knowns.** Artifact 4: each hypothesis has a statement, evidence for and against, confidence and status; at most five.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- **One** **`hypotheses`** **row each**, with an ordinal within the incident (H1–H4), a statement, the tests that would confirm or rule it out, a status, a confidence level and a reason for its status.
- **A link table,** **`hypothesis_evidence`****,** connects each hypothesis to evidence, marked **supports** or **contradicts**. One evidence item can support one hypothesis and contradict another.
- **Hypotheses are distinguished** by their ID and ordinal, never by their wording.
- **Status changes** (open → supported → ruled out, for example) increase the row's version, and each change is recorded as a timeline event, so its history can be replayed.

### Q7.6 The agent selects one likely explanation after evaluating evidence. How should the resulting diagnosis be represented?

**Frame.** What does a diagnosis record contain?

**Knowns.** Artifact 4: a leading hypothesis with confidence, alternatives, missing evidence; or an inconclusive status.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** A **`diagnoses`** **row**, with:

- `revision`: a new row for each revision, never an edit
- `outcome`: **established** or **inconclusive**
- `leading_hypothesis_id`: required if established, empty if inconclusive (enforced by the database)
- `confidence`, `summary`, `missing_evidence`
- `stop_reason`, for inconclusive results
- `reviewed` and `review_notes`, from the Diagnosis Reviewer
- `produced_by`: the component, and the model attempt that produced it

The leading hypothesis must belong to the same incident; a composite foreign key enforces this.

### Q7.7 A diagnosis explains the cause, but an action describes a proposed change. How should the platform distinguish these two objects?

**Frame.** How do we keep "what we believe" separate from "what we propose to do"?

**Knowns.** Artifact 1: approval applies to an action, not a diagnosis.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** **Two separate tables, with different lifecycles:**

|  | **Diagnosis** | **Action** |
| --- | --- | --- |
| Meaning | A belief about the cause | A proposed change to production |
| Changes production? | Never | Only after approval |
| Lifecycle | Revised as evidence changes | Proposed → tested → approved or rejected → executed → verified or undone |
| Approved? | No; reviewed | Yes, by a person |

Each action points to the diagnosis that justifies it (`diagnosis_id`). One diagnosis can have several actions; an action without a diagnosis can't exist.

### Q7.8 An agent proposes changing three lines of code. How should the resulting patch be represented and stored?

**Frame.** How is a patch stored?

**Knowns.** Artifact 4: patches go through the review system; approvals bind to the patch fingerprint.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- **The diff** is stored as a write-once artifact (the unified diff text).
- **A** **`patches`** **row** records:
    - the base revision it applies to
    - the diff's fingerprint (`diff_sha256`)
    - files changed, lines added and removed
    - the review reference (pull request)
- **Patches never change:** a revised patch is a new action, with a new patch.
- **Approvals name the fingerprint**, so any change to the diff voids them (Artifact 5).

### Q7.9 An investigation produces multiple possible changes. How should each proposed operation be represented independently?

**Frame.** How do several possible changes stay independent?

**Knowns.** Q7.7 and Q7.8.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** **Each proposed change is its own** **`actions`** **row**, with its own:

- kind (from the allowed list)
- target service and environment
- description, expected effect, risk and undo plan
- recovery criteria, recorded before any approval
- patch, test runs, approval request, execution attempts and verification
- status and version

Approving one action approves only that action. Rejecting one doesn't affect the others.

### Q7.10 A production action requires human authorization. What information should an approval record preserve?

**Frame.** What must an approval record keep?

**Knowns.** Artifact 4 and Artifact 5: authorised approver, recent sign-in, fingerprint, target, expiry, signature, second approver for high-impact changes.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** Two record types:

- **`approval_requests`****:** the action, the patch fingerprint, when it was requested, when it escalates and expires, how many approvers are needed, and why it closed.
- **`approval_decisions`**, one row per person:
    - the decision (approved or rejected) and the reason (required for rejections)
    - who decided, in what role, and when they last signed in
    - the exact patch fingerprint, target service and environment
    - when the decision was made, and when the approval expires (15 minutes)
    - the Approval Service's signature, and which key signed it

### Q7.11 A production action is attempted several times because of network failures. How should each attempt be represented?

**Frame.** How is each retry recorded?

**Knowns.** Artifact 4: each approved change executes at most once, through a unique execution key.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** **One** **`execution_attempts`** **row per attempt:**

- the same **`execution_key`** for every attempt of one approval, and an increasing **`attempt_no`**
- start and finish times, the outcome, the release process's reference, the error, and the stored response
- the database allows **only one attempt per key to end in "applied"**
- an attempt moves once from "started" to its final outcome, and can't be changed again

Undo operations are attempts too, marked `is_undo`.

### Q7.12 An external system returns an execution response. How should the platform preserve the execution outcome?

**Frame.** How do we keep what the release process told us?

**Knowns.** Artifact 5: after a crash, the platform looks up the outcome rather than guessing.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- **Store the raw response** as a write-once artifact (redacted).
- **Record the interpreted outcome** on the attempt:
    - **applied**
    - **not applied**
    - **failed**
    - **unknown**, when no response arrived
- **Record the release process's own reference** (`external_ref`), so the outcome can be checked there later.
- **Write an** **`execution.completed`** **event** in the same transaction.

An **unknown** outcome is never treated as success. It triggers the lookup in Artifact 5 (Q5.11).

### Q7.13 A repair needs to be evaluated against service health. How should the resulting verification record be represented?

**Frame.** What does a verification record contain?

**Knowns.** Artifact 4: criteria are recorded before execution; recovery must hold for the set period; the verifier is independent.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** A **`verifications`** **row**, with:

- the execution attempt it checks
- a **copy of the criteria** recorded before execution, such as "HTTP 500 rate on the failing path ≤ the pre-incident level"
- the hold period, and the measurement window
- the **measured values** for each criterion
- the result: **recovered**, **not recovered** or **inconclusive**
- the verifier's identity, and the person who accepted the result

Verification records are append-only.

### Q7.14 The model makes several calls during an investigation. Which information should be preserved for every model attempt?

**Frame.** What do we record about each model call?

**Knowns.** Artifact 4: cost and tokens per incident; 3 attempts per step; timing and tracing.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** One **`model_attempts`** **row** per call:

- the incident, the task (diagnose, review, draft patch) and the attempt number within the step
- the provider, the model, and the instructions' version
- the input's fingerprint, plus the stored input and output (redacted artifacts)
- the status: succeeded, invalid output, timeout, provider error, or refused by budget
- the validation errors
- input and output tokens, cost and latency
- the budget reservation it used, and the trace ID

These records let any diagnosis be **replayed**: same instructions version, same input, compare the output.

### Q7.15 The platform needs to limit financial exposure before executing model calls. How should budget reservations be represented?

**Frame.** How do we hold budget before a call, so limits can't be overrun?

**Knowns.** Artifact 4: per-incident limits are enforced before each call.

**Unknowns.** The exact price per token.

**Assumptions (provisional).**

- The maximum cost of a call can be calculated from its input size and its output limit. *Owner: SRE lead. Validated when: reserved and actual costs are compared on the test suite.*

**Answer.**

- **`incident_budgets`****:** one row per incident, with its limits, and what has been used, reserved and spent. Database checks make it impossible to exceed the limits.
- **Before each call:**
    1. Lock the budget row.
    2. Calculate the call's maximum cost.
    3. If it fits, create a **`budget_reservations`** row and add it to "reserved". If not, refuse the call.
- **After the call:** **settle** the reservation with the actual cost, and move it from reserved to spent.
- **If the call never returns**, the reservation **expires** and is released.

Money is stored as whole millionths of the currency unit, so there are no rounding errors.

### Q7.16 Multiple components need to communicate changes in incident state. How should those changes be represented as events?

**Frame.** What does a state-change event look like?

**Knowns.** Artifact 4: every action creates a timeline entry, which can't be edited.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** Every meaningful change creates one **event**, written in the same transaction as the change itself:

- a **CloudEvents envelope** (Q7.44) with a unique ID, a type, a source and a time
- a **per-incident sequence number** (Q7.47)
- **who acted**, and what caused it
- **a typed payload**, defined in the contracts

Events are named as past-tense facts, such as `aisre.approval.granted.v1`. They're stored in `timeline_events`, which is the public history (section 7.5 lists every type).

### Q7.17 An investigation produces large logs, reports and patch files. How should the platform reference and manage these artifacts?

**Frame.** How are large items referenced and managed?

**Knowns.** Artifact 6 (ADR-18): a write-once object store; the record keeps references and fingerprints. Artifact 4: 30-day retention for raw evidence.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- **The content** goes in the object store, under an internal key.
- **An** **`artifacts`** **row** records:
    - its kind and media type
    - size and fingerprint
    - whether it was redacted
    - its retention date
- **Other records refer to** **`artifact_id`****,** never to the storage key.
- **Write-once:** content and metadata never change.
- **Retention:** a separate job deletes expired items. The application's own database role can't delete them.

### Q7.18 The incident lifecycle contains incidents, evidence, hypotheses, diagnoses, patches, approvals and execution attempts. Which of these should become independent PostgreSQL tables?

**Frame.** Which objects get their own table?

**Knowns.** Each has its own identity, lifecycle or many-to-one relationship (Part A).

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** **All of them**, because each has its own identity and is referenced by others. The full list:

- **Catalogue:** `services`, `environments`
- **Incident:** `incidents`, `incident_alerts`
- **Evidence and reasoning:** `evidence`, `hypotheses`, `hypothesis_evidence` (link), `diagnoses`
- **Change:** `actions`, `patches`, `test_runs`
- **Approval:** `approval_requests`, `approval_decisions`
- **Execution and verification:** `execution_attempts`, `verifications`
- **Model use:** `model_attempts`, `incident_budgets`, `budget_reservations`
- **Support:** `artifacts`, `timeline_events`, `outbox`, `idempotency_keys`

What varies by kind stays inside a row as JSONB (Q7.26).

### Q7.19 A diagnosis belongs to an incident, but an incident may have multiple diagnoses. How should the database enforce this relationship?

**Frame.** How does the database enforce "many diagnoses, one incident"?

**Knowns.** Q7.6.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- `diagnoses.incident_id` is a **required foreign key** to `incidents`.
- `UNIQUE (incident_id, revision)` gives each diagnosis a revision number within its incident.
- **Composite foreign keys** stop cross-incident links:
    - a diagnosis's leading hypothesis must belong to the same incident
    - an action's diagnosis must belong to the same incident
- The current diagnosis is the **highest revision**, so no "current" flag can fall out of step.

### Q7.20 Two incoming requests accidentally attempt to create the same incident. Which database constraints could prevent duplicate records?

**Frame.** What stops two identical incidents?

**Knowns.** Artifact 4: one investigation per deduplication key; idempotent submission.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** Two independent protections:

- **A partial unique index:** only one *open* incident per `(org_id, dedup_key)`. A second insert fails, and intake attaches the alert to the existing incident instead.
- **Idempotency keys:** a primary key on `(caller_id, operation, idem_key)`, so a retried request returns the original result (Q7.61).

Both run inside one transaction. Of two concurrent requests, one wins, and the other receives the winner's incident.

### Q7.21 Approval decisions and execution history must remain auditable. Which records should be immutable?

**Frame.** Which rows may never change?

**Knowns.** Artifact 5: append-only audit; hash chain.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

| **Immutable (no update, no delete)** | **Change once, then frozen** | **Mutable (versioned)** |
| --- | --- | --- |
| `timeline_events`, `approval_decisions`, `evidence`, `patches`, `test_runs`, `verifications`, `model_attempts`, `artifacts` | `execution_attempts` (started → final outcome) | `incidents`, `hypotheses`, `actions`: status and version only, with every change also written as an event |

**Enforcement:**

- database triggers reject changes
- the application's database role has no delete rights on these tables
- the hash chain on `timeline_events` makes any tampering detectable

### Q7.22 An incident has hundreds of evidence records and several patch candidates. How should relationships between these records be represented?

**Frame.** How are the many links between records modelled?

**Knowns.** Part A.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- **One-to-many** through foreign keys:
    - incident → evidence, hypotheses, diagnoses, actions
    - action → patch, test runs, approvals, attempts, verifications
- **Many-to-many** through a link table: `hypothesis_evidence`, marked supports or contradicts.
- **Indexes** on `(incident_id, kind)` and on time, so an incident's evidence loads quickly.
- **Paged reads** in the API, so hundreds of items aren't returned at once.

### Q7.23 An engineer needs to inspect every previous approval decision. How should approval history be stored?

**Frame.** How do we keep a complete approval history?

**Knowns.** Q7.10, Q7.21.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- **Every decision is a new** **`approval_decisions`** **row.** Nothing is overwritten, including rejections, and decisions on actions later withdrawn.
- **Requests keep their closing reason:** decided, expired, withdrawn, or voided because the patch or service changed.
- **Each decision is also a timeline event.**
- **Query by action, incident, approver or time**, using indexes on `(action_id, decided_at)`.

### Q7.24 Two workers attempt to update the same incident simultaneously. How should the database prevent inconsistent updates?

**Frame.** How do we stop two workers overwriting each other?

**Knowns.** Artifact 4: safe resume after crashes; one execution per approval.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- **Only the workflow changes an incident's status.** A single workflow per incident (workflow ID `incident-<incident_id>`) means there is normally only one writer.
- **Optimistic concurrency, for every update:** `UPDATE ... SET ..., version = version + 1 WHERE incident_id = $1 AND version = $2`. If no row changes, someone else changed it first: reload and decide again.
- **Row locks (****`SELECT ... FOR UPDATE`****)** for short critical sections:
    - adding an event (to take the next sequence number)
    - reserving budget
- **Unique constraints** as a final guard (Q7.20, Q7.11).

### Q7.25 An incident progresses through several states, and two components attempt to modify it concurrently. How should state versions be tracked?

**Frame.** How do we track which version of the state each change was based on?

**Knowns.** Q7.24.

**Unknowns.** The full state machine (Layer 8).

**Assumptions (provisional).** None needed.

**Answer.**

- **A** **`version`** **column** on `incidents`, `actions` and `hypotheses`, increased on every change.
- **Every change states the version it expects.** The API takes it as an `If-Match` header; the worker passes it in its update.
- **Every state change writes an event** with the old and new state, and the new version. The full history can therefore be replayed.
- **Allowed transitions are checked in code** before writing (defined in Layer 8). An invalid transition is rejected, even if the version matches.

### Q7.26 Some information is highly structured while other information varies between evidence types. Which fields should be normalized into columns, and which could be represented using JSONB?

**Frame.** What goes in columns, and what in flexible JSON?

**Knowns.** Q7.3.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

| **Columns** | **JSONB** |
| --- | --- |
| Anything used to join, filter, enforce or audit: IDs, status, kind, times, fingerprints, service, environment, decision, outcome | Evidence `attributes` that differ by kind |
| Approval fields (so constraints apply) | Recovery criteria and measured values |
| Costs and tokens | Event payloads (`data`), validated by the contracts |
| Anything a constraint must check | Raw alert payloads |

**Rule:** if the database must enforce it, or a query filters on it often, it's a column. JSONB is always validated by a Pydantic contract before being written, and indexed with GIN where it's searched.

### Q7.27 The application schema changes as new features are introduced. How should database migrations be managed without losing existing information?

**Frame.** How do we change the schema safely?

**Knowns.** Artifact 6 (ADR-05): Alembic, expand then contract.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- **Every change is a reviewed Alembic migration.** The first migration is `schema.sql`.
- **Expand, then contract:** add new columns and tables first; deploy code that writes both; copy old data across in batches; switch reads; remove old columns in a later release.
- **Never rewrite immutable tables:** add columns with defaults instead.
- **Event payloads carry a** **`schema_version`****,** so old events still read correctly.
- **Test every migration** against a copy of production data before applying it.
- **Back up** (point-in-time recovery) before every migration.

### Q7.28 An external monitoring system needs to submit an incident. Which endpoint and request contract should the platform expose?

**Frame.** How does monitoring submit an incident?

**Knowns.** Artifact 4: mandatory fields; deduplication; idempotency; p95 ≤ 300 ms.

**Unknowns.** Whether the monitoring system can send custom headers.

**Assumptions (provisional).**

- Monitoring can send an authorisation header and an idempotency key. *Owner: Platform owner. Validated when: a test alert is sent with both.*

**Answer.** **`POST /v1/incidents`**

- **Headers:** `Authorization` (the monitoring system's identity) and `Idempotency-Key`.
- **Body:** `IncidentCreate`, with service, environment, started_at, title and source required; alert ID, fingerprint, severity hint and links optional. Unknown fields are rejected.
- **Responses:**
    - `201 Created`: a new incident, with an `IncidentAccepted` body and a `Location` header
    - `200 OK`: the alert joined an existing open incident (`deduplicated: true`)
    - `422`: invalid fields
    - `403`: service not allowed
    - `409`: same idempotency key, different body
- **If monitoring can't send headers,** a small adapter (in Intake) maps its payload to this contract, and derives the idempotency key from the alert's ID.

### Q7.29 An engineer needs to inspect an existing incident. How should the API retrieve its current state?

**Frame.** How does an engineer read an incident's current state?

**Knowns.** Artifact 4: the CLI and API show the incident.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** **`GET /v1/incidents/{incident_id}`** returns `IncidentView`:

- status, severity (proposed and confirmed), service and environment
- the current diagnosis ID, and open actions
- budget use
- `version`, and an `ETag` header (used for `If-Match`)
- `last_event_seq`, which shows how far the timeline has got

Related endpoints:

- `GET /v1/incidents/{id}/diagnoses/current`
- `GET /v1/incidents/{id}/actions`
- `GET /v1/incidents/{id}/evidence?kind=&cursor=`
- `GET /v1/incidents?service=&status=&cursor=`

### Q7.30 An engineer wants to reconstruct the complete investigation. How should the API expose its event timeline?

**Frame.** How does the API return the whole history?

**Knowns.** Q7.16.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** **`GET /v1/incidents/{incident_id}/timeline?after_seq=0&limit=200`**

- Returns events in sequence order, as CloudEvents, with a `next_after_seq` value for the next page.
- Filter with `types=`.
- **`GET /v1/incidents/{id}/timeline/stream`** gives live updates (Q7.52).

### Q7.31 An engineer needs to review an AI-generated patch. How should the API expose the corresponding artifact safely?

**Frame.** How does an engineer see a patch safely?

**Knowns.** Artifact 5: only authorised users see an incident's material; content is redacted.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- **`GET /v1/actions/{action_id}`** returns the action and its `PatchView`: fingerprint, size, files changed, review link and artifact ID.
- **`GET /v1/artifacts/{artifact_id}`** returns metadata only (`ArtifactView`).
- **`GET /v1/artifacts/{artifact_id}/content`**:
    - checks permission for the artifact's incident
    - streams the content as **plain text**, with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`, so it's never run or rendered as a page
    - returns the fingerprint in a header, so the reviewer can check it matches the approval

### Q7.32 An engineer wants to authorize a proposed production action. Which API operation should accept the approval?

**Frame.** Which call records an approval?

**Knowns.** Artifact 4 and Artifact 5: authorised approver, recent sign-in, exact fingerprint, signed.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** **`POST /v1/actions/{action_id}/approvals`** with `ApprovalCreate`:

- the **patch fingerprint** the approver reviewed
- the action **version** they saw
- an optional note

The API checks:

- the approver's role for the target service
- that they signed in within the last 15 minutes
- that it isn't self-approval
- that the fingerprint and version match the current action
- that the request is open

**Response:** `201` with `ApprovalDecisionView`. The approval, its signature, its event and its outbox signal are written in one transaction. The workflow receives the signal through the outbox. Failures: `403` (not allowed), `409` (fingerprint or version changed, or the request is closed), `401` (sign-in too old).

### Q7.33 An engineer determines that a proposed patch is unsafe. How should the API record the rejection?

**Frame.** How is a rejection recorded?

**Knowns.** Q7.10.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** **`POST /v1/actions/{action_id}/rejections`** with `RejectionCreate`:

- the patch fingerprint
- a **required reason**
- whether more evidence is wanted

It creates an immutable `approval_decisions` row (`decision = rejected`), closes the request, sets the action to **rejected**, and signals the workflow. The workflow either gathers the requested evidence, or hands over. The rejection is never deleted.

### Q7.34 An operator needs to stop an ongoing investigation. How should cancellation be requested?

**Frame.** How is cancellation requested?

**Knowns.** Artifact 4: stop within 30 seconds; never half-apply a change; idempotent.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.** **`POST /v1/incidents/{incident_id}/cancellation`** with a reason.

- `Idempotency-Key` header; repeating it returns the same result.
- The API records a **cancellation-requested** event and an outbox signal, and returns `202 Accepted`.
- The workflow stops at the next safe point, and records **cancelled**.
- **`GET /v1/incidents/{id}`** shows the final status.

It's modelled as creating a cancellation, not as deleting the incident, because the incident and its record stay.

### Q7.35 An orchestrator needs to determine whether the API process is running. Which endpoint should expose this information?

**Frame.** How do we show the process is alive?

**Answer.** **`GET /livez`** returns `200` if the process is running and its event loop responds. It checks **nothing else**, so a database outage doesn't cause restarts that make things worse. No authentication; reveals nothing.

### Q7.36 A deployment system needs to determine whether the API is ready to accept traffic. How should readiness be exposed?

**Frame.** How do we show the API can take requests?

**Answer.** **`GET /readyz`** returns `200` only when:

- the database answers
- the schema is at the expected migration
- configuration and the approval signing key are loaded

Otherwise it returns `503`, with which check failed. Temporal isn't required for readiness, because the outbox lets intake work while Temporal is down. No authentication; it reveals only check names.

### Q7.37 The observability stack needs access to application metrics. Which endpoint should expose them?

**Frame.** Where does monitoring collect the platform's metrics?

**Answer.** **`GET /metrics`** in Prometheus format, on a **separate internal port** that isn't exposed outside the platform's network. It carries request counts and latency, outbox backlog and age, workflow queue length, budget use, and limit breaches. Labels never include personal data or secrets; incident IDs go in traces, not metric labels, to keep their number bounded.

### Q7.38 An API request fails because the user lacks permission. How should the platform communicate this failure consistently?

**Frame.** How do we report errors the same way every time?

**Answer.** Every error uses **RFC 9457 problem details** (`application/problem+json`), the `Problem` contract:

- `type`, `title`, `status`, `detail`
- a stable `code`, such as `forbidden_service`
- the `request_id`

| **Status** | **When** |
| --- | --- |
| `401` | Not signed in, or the sign-in is too old for this action |
| `403` | Signed in, but not allowed |
| `404` | Not found, **or not allowed to know it exists** (for incidents on other services) |
| `409` | Version, fingerprint or idempotency conflict |
| `422` | Invalid fields, listed in `errors` |
| `429` | Rate limited |
| `503` | Temporarily unavailable |

Error messages never reveal internal details.

### Q7.39 Different user types need different access rights. How should authentication and authorization be incorporated into API design?

**Frame.** How are identity and permissions built into the API?

**Knowns.** Artifact 5: single sign-on with two-factor; roles per service; the executor checks again.

**Unknowns.** None.

**Assumptions (provisional).** None needed.

**Answer.**

- **Authentication:** every request carries a short-lived **OIDC bearer token** from the organisation's identity system. Systems (monitoring, the CLI in automation) use their own client credentials.
- **Authorization:** one check runs for every endpoint, and names the permission it needs: for example `incident:create`, `incident:read`, `action:approve`, `incident:cancel`.
- **Roles per service:** viewer, responder, approver, incident lead, plus the monitoring system's role.
- **Approvals need extra checks:** recent sign-in, and no self-approval.
- **Denials are logged.**

| **Endpoint group** | **Viewer** | **Responder** | **Approver** | **Incident lead** | **Monitoring** |
| --- | --- | --- | --- | --- | --- |
| Read incidents, timeline, artifacts | ✓ | ✓ | ✓ | ✓ | — |
| Create incident | — | ✓ | ✓ | ✓ | ✓ |
| Approve or reject an action | — | — | ✓ | ✓ | — |
| Cancel an investigation | — | ✓ | ✓ | ✓ | — |
| Confirm severity, close | — | — | — | ✓ | — |

### Q7.40 External integrations depend on API contracts that may evolve over time. How should the platform support versioning?

**Frame.** How do we change the API without breaking clients?

**Answer.**

- **A major version in the path:** `/v1`.
- **Additive changes stay in v1:** new optional fields and new endpoints. Clients must ignore response fields they don't know.
- **Breaking changes need** **`/v2`****,** run alongside v1 for a stated period. v1 responses then carry `Deprecation` and `Sunset` headers.
- **Event types carry their own version** (`...v1`), changed the same way.
- **The OpenAPI description is generated** from the contracts, and checked in the build, so an accidental breaking change fails the build.

### Q7.41 An engineer requests a patch artifact, but its internal filesystem path is exposed in the response. How should artifact access be abstracted?

**Frame.** How do we stop internal storage details leaking?

**Answer.**

- **Only** **`artifact_id`** **is ever returned.** The storage key exists only in the database, and is never in a contract.
- **Content is fetched through the API** (`/v1/artifacts/{id}/content`), which checks permission each time.
- **If direct download is needed later,** the API returns a **short-lived signed link** (provisional: 5 minutes), never a permanent path.
- **A build check** fails if any response contract contains a field named like a path or storage key.

### Q7.42 An incident passes through 20 operations, but the dashboard only shows its current status. How could engineers reconstruct the entire history of the investigation?

**Frame.** How do we keep the full history, not just the current state?

**Answer.** Every operation writes an **event** to `timeline_events`, in the same transaction as its change. The current state lives in the incident's tables; the history lives in the events. Reading the events in sequence reconstructs every step: what happened, who did it, why, and when. The timeline endpoints (Q7.30) and the export make it available.

### Q7.43 Multiple components need to react when an incident changes state. How could the architecture support event-driven communication?

**Frame.** How do components react to changes without calling each other directly?

**Answer.**

- **Work is driven by the workflow:** the Temporal workflow decides each next step and calls components as activities. Most "reactions" are steps in it.
- **Outside the workflow:**
    - the outbox delivers start and signal messages to Temporal (Q7.57)
    - the Notifier and the live stream read `timeline_events`
- **Database notifications (****`LISTEN/NOTIFY`****)** wake readers when a new event is written. They then read from the table, which stays the source of truth. A missed notification only delays a reader; nothing is lost.

This gives event-driven behaviour without a separate message broker (Q7.64).

### Q7.44 Several independent systems need to exchange events with consistent metadata. Which standard could provide a common event envelope?

**Frame.** Which standard should event envelopes follow?

**Answer.** **CloudEvents 1.0**, in its structured JSON form. It defines common attributes: `id`, `source`, `type`, `specversion`, `subject`, `time`, `datacontenttype`, `dataschema`. It allows lower-case extension attributes for our own fields. It's widely supported, so events can later be sent to other tools without translation.

### Q7.45 An event is generated by the workflow engine, but downstream consumers cannot identify its source or destination. Which common fields should every event contain?

**Frame.** What metadata must every event carry?

**Answer.**

| **Field** | **Meaning** |
| --- | --- |
| `id` | Unique per occurrence |
| `source` | The producing component, for example `/aisre/worker/recovery-verifier` |
| `type` | What happened, with a version, for example `aisre.verification.completed.v1` |
| `subject` | What it's about: `incidents/<incident_id>` |
| `time` | When it happened |
| `incidentid`, `orgid` | Which incident and organisation |
| `sequence` | Position within the incident |
| `actor` | The person or component that acted |
| `correlationid` | Groups related events (usually the incident ID) |
| `causationid` | The event or request that caused this one |
| `traceparent` | Links to the distributed trace |
| `data` | The typed payload |

Events describe facts and don't name destinations. Consumers decide whether to react.

### Q7.46 Two events have identical payloads but represent different occurrences. How should each event be uniquely identified?

**Frame.** How do we tell apart two events that look the same?

**Answer.**

- **Every occurrence gets a new** **`id`** **(UUIDv7)** when it's created, never derived from its content. Two identical alerts are two events.
- **`(incident_id, sequence)`** is also unique, and gives each event its position.
- **When a step is retried, the same occurrence keeps its original ID.** The ID is created with the change, in the same transaction, so a retry that already succeeded doesn't create a second event.

### Q7.47 Events arrive in a different order from the order in which operations occurred. How should sequencing be handled?

**Frame.** How do we keep events in the right order?

**Answer.**

- **The sequence number defines the order, not the timestamp.** Clocks differ between machines, so `time` is for information only.
- **Taking a number:** the writer locks the incident row, increases `last_event_seq`, and writes the event with that number, all in one transaction. Numbers are therefore gapless and in commit order.
- **Consumers process events in sequence order**, and store the last number they handled.

### Q7.48 Several incidents progress simultaneously. Should events be globally ordered or ordered independently within each incident?

**Frame.** One global order, or one order per incident?

**Answer.** **Per incident.**

- Only events within an incident depend on each other.
- A global order would make every incident wait on one counter, and limit concurrency.
- Per-incident order is enough to replay any incident exactly.

Where a cross-incident view is needed (reports), events are sorted by `recorded_at`, and the order of unrelated incidents doesn't matter.

### Q7.49 A consumer receives the same event multiple times. How should it prevent duplicate processing?

**Frame.** How does a consumer ignore repeats?

**Answer.**

- **Record what's been processed:** each consumer stores the last sequence it handled per incident, or the event IDs it has processed, **in the same transaction as its own effect**.
- **Skip anything already handled.**
- **Make effects idempotent where possible:** for example, a notification carries the event ID, so the messaging tool can drop repeats.
- **Workflow signals carry the approval or cancellation ID,** and the workflow ignores IDs it has already seen.

### Q7.50 A consumer receives an event before receiving an earlier event. How should it detect and handle out-of-order delivery?

**Frame.** How does a consumer spot and handle a missing earlier event?

**Answer.**

- **Detect:** the event's sequence is higher than the last processed sequence plus one.
- **Handle:**
    - **don't process it yet**
    - fetch the missing events from `timeline_events` (the table always has them), then process them all in order
- **Events with a sequence at or below the last processed** are duplicates, and are skipped (Q7.49).

Because the table is complete and gapless, a gap is always a delivery delay, never lost data.

### Q7.51 A dashboard disconnects while receiving an incident timeline. How should it resume receiving updates without losing events?

**Frame.** How does a stream reconnect without missing anything?

**Answer.**

- **Each streamed event carries its sequence as the SSE** **`id`****.**
- **On reconnect,** the browser or CLI sends **`Last-Event-ID`** automatically. The server replays every event after that number from `timeline_events`, then continues live.
- **A client can also pass** **`?after_seq=`** explicitly.
- **The server sends** **`retry`** (provisional: 3 seconds) so clients wait before reconnecting.

### Q7.52 An engineer needs to receive real-time incident updates without repeatedly polling the API. Which streaming mechanism could support this?

**Frame.** How do we push live updates?

**Answer.** **Server-Sent Events (SSE)** at `GET /v1/incidents/{id}/timeline/stream`.

- Updates only flow from the server to the client, which is exactly SSE's model.
- It works over ordinary HTTP, through proxies.
- It has built-in reconnection with `Last-Event-ID`.
- It's simple to use from the CLI and from any future interface.

**WebSockets** aren't needed, because the client never sends messages over the stream; commands use normal API calls. The design is in 7.9.

### Q7.53 The Temporal workflow engine maintains its own execution history. Why would exposing that internal history directly as the public incident timeline create architectural coupling?

**Frame.** Why not show Temporal's history as the incident timeline?

**Answer.**

- **It describes the machinery, not the incident:** activity attempts, timers, internal retries and serialised inputs, rather than "the approver approved patch X".
- **Its format belongs to Temporal,** and could change with upgrades. Clients would depend on it.
- **It would tie us to Temporal.** ADR-06 keeps a fallback to a PostgreSQL job queue; a public history in Temporal's format would make that switch break every client.
- **It's kept for a limited time,** and may be reset or replayed. The incident record must last a year.
- **It isn't scoped by our permissions,** and may contain unredacted inputs.
- **Some events don't come from the workflow at all:** approvals and cancellations come from the API.

So the platform writes its **own events**, in its own contracts, and treats Temporal's history as an internal debugging tool.

### Q7.54 PostgreSQL successfully creates an incident, but Temporal becomes unavailable before the corresponding workflow starts. How can the platform prevent the incident from remaining permanently unprocessed?

**Frame.** How do we make sure every stored incident gets its workflow?

**Answer.** **Use the transactional outbox (Q7.57):**

1. The API writes the incident, its first event, and an **outbox row** ("start workflow `incident-<id>`") in one transaction.
2. The outbox relay delivers it whenever Temporal is available, retrying with backoff.
3. **A safety check** alerts if any incident stays "open" with no workflow after a set time (provisional: 2 minutes).

### Q7.55 Temporal successfully starts a workflow, but PostgreSQL fails to save the corresponding incident record. How could this create inconsistent application state?

**Frame.** What goes wrong if the workflow exists but the incident doesn't?

**Answer.** If the API started the workflow first, and then the database write failed:

- a workflow would run for an incident that **doesn't exist** in the record
- it could collect evidence, call the model and spend budget, with **no record, timeline or audit**
- engineers couldn't see it, approve it or cancel it through the API
- a retry would create the incident, and possibly **a second workflow**

**Prevented by ordering:**

- The record is always written first; the workflow is started only from the outbox, after the commit.
- The workflow's first step loads the incident. If it doesn't exist, the workflow ends immediately, and reports the error.

### Q7.56 Two independent systems need to commit related changes. Why would an ordinary PostgreSQL transaction be insufficient to guarantee atomicity across both systems?

**Frame.** Why can't one database transaction cover both PostgreSQL and Temporal?

**Answer.**

- **A PostgreSQL transaction only covers PostgreSQL.** Temporal has its own storage and its own commits, so a rollback in one can't undo the other.
- **Calling Temporal inside the transaction doesn't help:**
    - the call may succeed and then the commit fail, which is Q7.55
    - the commit may succeed and then the call never happen, which is Q7.54
    - the transaction would also be held open during a network call
- **Two-phase commit across both isn't supported** by Temporal, and would tie the two systems' availability together.

The answer is to commit to **one** system (PostgreSQL), and deliver to the other **reliably, at least once, with idempotent receipt**.

### Q7.57 The API needs to save an incident and reliably arrange for a background workflow to start, even if the process crashes between these operations. Which transactional messaging pattern could solve this?

**Frame.** Which pattern makes "save and start" reliable?

**Answer.** **The transactional outbox.**

- In the same database transaction as the incident, write an **outbox row** describing the message to send.
- If the transaction commits, the message is guaranteed to exist. If it rolls back, neither exists.
- A separate **outbox relay** reads pending rows, delivers them to Temporal, and marks them delivered.
- Delivery is **at least once**. Duplicates are made harmless by stable workflow IDs, and by signal IDs (Q7.63).

The same pattern is used for approval, rejection and cancellation signals. The design is in 7.7.

### Q7.58 A durable event has been stored but has not yet been delivered to Temporal. How should a background dispatcher discover and process pending events?

**Frame.** How does the relay find and send pending messages?

**Knowns.** The relay runs inside the worker process (no new process; Artifact 6).

**Unknowns.** None.

**Assumptions (provisional).**

- Polling every second, plus a database notification, meets the 1-second delivery target. *Owner: Platform owner. Validated when: the load test measures event publication latency (NFR-31).*

**Answer.**

1. **Wake up** on a database notification, or every second.
2. **Claim a batch:** `SELECT ... FROM outbox WHERE delivered_at IS NULL AND available_at <= now() ORDER BY outbox_id LIMIT 50 FOR UPDATE SKIP LOCKED`. Several relay instances can run without taking the same rows.
3. **Deliver each message** to Temporal: start the workflow, or send a signal.
4. **On success,** set `delivered_at`.
5. **On failure,** increase `attempts`, record the error, and set `available_at` later (exponential backoff, capped at 1 minute).
6. **Alert** if the oldest pending message is older than 2 minutes, or if a message fails 20 times.
7. **Delete delivered rows** after 7 days.

Messages for one incident are delivered in `outbox_id` order. The relay processes rows for the same incident one at a time.

### Q7.59 The dispatcher starts a Temporal workflow successfully but crashes before marking the event as delivered. What should happen when the dispatcher restarts?

**Frame.** What happens after the relay crashes between "sent" and "marked sent"?

**Answer.**

- **The row is still pending**, so the relay **sends it again**. This is expected: delivery is at least once.
- **Starting the workflow again** uses the same workflow ID. Temporal reports "already started", which the relay treats as **success**, and marks the row delivered.
- **Signals again:** the signal carries the approval or cancellation ID, and the workflow ignores IDs it has already processed.

No duplicate workflow, and no duplicate action.

### Q7.60 An API request is repeated because the client never received the original response. How could the system ensure that repeating the same operation does not produce duplicate effects?

**Frame.** How do we make a repeated request harmless?

**Answer.**

- **Every write endpoint requires an** **`Idempotency-Key`** **header** (creating incidents, approvals, rejections and cancellations).
- **The first request** stores the key with its outcome.
- **A repeat** with the same key and body returns the **stored response**, and does nothing else.
- **Natural protections back this up:**
    - one open incident per deduplication key
    - one decision per approver per request
    - one execution per approval

The rules are in 7.8.

### Q7.61 Multiple requests need to be recognized as attempts to perform the same logical operation. How should an idempotency key be generated, stored and enforced?

**Frame.** How are idempotency keys created, kept and checked?

**Answer.**

- **Generated by the client,** once per logical operation:
    1. **people and the CLI:** a random UUID, reused for every retry of that operation
    2. **monitoring:** derived from the alert's own ID and firing time
- **Stored** in `idempotency_keys`:
    1. **key:** caller, operation and key
    2. the request's fingerprint
    3. state (in progress, completed), the stored response, and the resource created
    4. an expiry (24 hours)
- **Enforced:**
    1. Insert the key as **in progress**, in the same transaction as the operation.
    2. If the key already exists:
        - **completed** with the same fingerprint: return the stored response
        - **in progress**: return `409` with "retry later"
        - **different fingerprint**: Q7.62
    3. On commit, store the response.
- **Keys are scoped to the caller**, so one caller can't replay another's.

### Q7.62 A client reuses an existing idempotency key but sends a completely different payload. How should the API respond?

**Frame.** What if a key is reused with a different request?

**Answer.** **Reject it with** **`409 Conflict`**, code `idempotency_key_reused`, and do nothing.

- The fingerprint is calculated from the **canonical** body: fields sorted, with whitespace and field order ignored.
- Never apply the new request, and never return the old response, because either would hide a client bug.
- The response says which key conflicted, and when it expires.

### Q7.63 The dispatcher retries workflow creation after losing the previous response. How could a stable workflow identifier prevent duplicate workflow creation?

**Frame.** How does a fixed workflow ID stop duplicates?

**Answer.**

- **The workflow ID is derived from the incident:** `incident-<incident_id>`, never random.
- **Temporal allows only one running workflow per ID.** A second start with the same ID fails with "already started", which the relay treats as success.
- **The reuse policy rejects duplicates**, so even a closed workflow can't be accidentally restarted for the same incident. A deliberate re-investigation would use a new, recorded workflow ID (`incident-<id>-r2`).
- **Activities use their own stable keys** (for example, the execution key), so retries inside the workflow are safe as well.

### Q7.64 The team proposes Kafka to solve event delivery, but the initial platform has modest event volume. Under what workload or architectural conditions would Kafka become justified, and when would PostgreSQL plus an outbox be sufficient?

**Frame.** When would Kafka be worth it, and when is the outbox enough?

**Knowns.**

- Artifact 2: low volume; 5 concurrent investigations.
- Artifact 6 (Q6.33): no message broker initially.

**Unknowns.** Future event volume and the number of consumers.

**Assumptions (provisional).**

- The first version produces fewer than 50,000 events a day. *Owner: Platform owner. Validated when: measured during the pilot.*

**Answer.**

**PostgreSQL plus the outbox is enough when:**

- event volume is modest: thousands to low millions a day
- there are a few consumers, all owned by this team
- per-incident ordering is enough
- the events table can be replayed directly
- the team doesn't want to run another distributed system

**Kafka becomes justified when** several of these are true, and measured:

- sustained event rates that strain the database: tens of thousands a second, or outbox delay above its target
- many independent consumers, owned by other teams, each reading at its own pace
- long replay of high-volume streams, across many consumers
- streaming or analytics processing of events, across systems
- multiple platform instances or organisations, exchanging events

**Even then, the outbox stays.** It's what makes publishing reliable; Kafka would replace only the delivery step. Moving would be recorded as a new decision.
